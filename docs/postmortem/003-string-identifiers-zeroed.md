# 003 — 字符串型标识符静默解成 0

## 摘要

NCM 的 `musicId`、`albumId`、artist id 等字段可能被编码成 JSON 数字，也可能被编码成**字符串**（真实新样本里全是 `"2164260966"` 这种形态）。`Int64.UnmarshalJSON` 本应有「先按整数解析、失败再处理字符串」的回退，但一处 nil map 让字符串回退路径**永远走不到**，带引号的 id 全部静默解成 `0`——不报错、不 panic，只是值错了。

## 影响

- 曲目/专辑/艺人的标识符全部丢失，`--output-template` 的 `{id}` 会产出错误的文件名。
- 属于静默错误：转换照常完成，只有比对元数据时才发现。

## 根因分析（blameless）

- **Why 值变成 0？** 字符串形态没有走到「去引号后再解析」的分支。
- **Why 走不到？** 该分支依赖的一个 map 为 nil，判定因此恒为假，回退被旁路。
- **Why 是静默的？** `UnmarshalJSON` 里空串与 `null` **合法地**映射为 0，于是「解析失败误入 0」和「确实是 0」无法区分。
- **Why 测试没早发现？** 需要同时构造「带引号的 id」和「数字形态的样本」来对照；只测数字形态永远绿。

**贡献因素**：`Int64` 把「合法空值→0」与「解析失败→0」混在一个出口；NCM 对同一字段在不同样本里用不同 JSON 类型。

## 做得对的地方

- 修复后测试**同时断言**数字、带引号数字、带引号浮点、null、空串与非法输入六类，并覆盖 artist id 的字符串形态。
- 「先 `ParseInt(...,64)` 再兜 `ParseFloat`」的写法保证了不丢大整数精度。

## 教训

NCM 的标识符既可能是数字也可能是字符串，回退路径必须真实可达；不要用「解析失败→0」这种与合法空值同出口的写法掩盖错误。
