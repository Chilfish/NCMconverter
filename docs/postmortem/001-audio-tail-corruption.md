# 001 — 音频反混淆尾部被破坏

## 摘要

`Converter.HandleMusic` 按 `0x8000` 字节一块解除音频混淆。混淆的密钥盒位置**在每个块开头重置**，因此每块的下标必须用「块内相对偏移」计算。若按整块长度写出（而不是按实际剩余长度），最后一块会被补齐陈旧字节并丢掉真正的尾块——产物仍能播放，但尾部被静默破坏。

## 影响

- **数据完整性**：转换产物不是源音频的逐字节还原。对静默尾部的破坏，播放器往往照常播放，用户很难察觉。
- 属于「看起来成功、实际有损」的一类错误，比直接报错更危险。

## 根因分析（blameless）

- **Why 尾部会错？** 反混淆按块循环，若每块都按固定块大小处理，不足一块的尾块就会读越界或被补零。
- **Why 容易写错？** 下标 `j` 用的是**块内相对偏移**（`byte(i - off + 1)`），而不是相对文件；块首必须重置密钥盒位置。这种「看起来多此一举」的减法一旦漏掉或算错，块边界就崩。
- **Why 没有立刻发现？** 只要音频总长是块大小的整数倍，错误就不显现；真实样本、合成样本的长度组合不固定，需要专门构造边界。

**贡献因素**：块大小是常量、反混淆是自逆变换（对拍容易掩盖细节）、早期没有覆盖块边界的测试。

## 做得对的地方

- 错误最终被一条**参数化边界测试**抓住并锁定：`0 / 1 / 0x8000-1 / 0x8000 / 0x8000+1 / 2*0x8000+1234` 六种长度，断言输出长度与内容都精确相等。

## 教训

混淆的密钥盒位置在每个 `0x8000` 块开头重置；任何按整块写出或漏读末块的做法都会静默毁掉音频尾部。改动前先跑块边界测试。
